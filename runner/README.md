# Сборочная машина

Здесь живёт GitLab-раннер, который прогоняет тесты, собирает образы и
запускает выкладку. Отдельно от прод-сервера: сборке фронтенда нужно около
двух гигабайт только на себя, и на проде она конкурировала бы за память с
работающим сайтом.

Что нужно от машины: docker и гигабайта четыре памяти. Диск — гигабайт
двадцать: там оседают образы и кеш сборок.

## Установка

```bash
# Docker, если его нет
curl -fsSL https://get.docker.com | sh

# Забрать эту папку на машину, дальше из неё
mkdir -p config
cp config.toml.example config/config.toml
```

Завести раннер в интерфейсе проекта: **Settings → CI/CD → Runners → New
project runner**.

- **Tags:** `study-platform` — ровно этот тег стоит у всех джоб в
  `.gitlab-ci.yml`. Не совпадёт — джобы уедут на общие раннеры gitlab.com и
  съедят бесплатные минуты, ради экономии которых раннер и заводится.
- **Run untagged jobs:** не включать, по той же причине.

GitLab покажет токен вида `glrt-…`. Вписать его в `config/config.toml` вместо
`glrt-PASTE_TOKEN_HERE` и поднять:

```bash
docker compose up -d
docker compose logs -f runner
```

В логе должно появиться `Configuration loaded` и `Checking for jobs... received`
при первом же пайплайне. `couldn't execute POST … 403` означает, что токен не
подошёл.

Команда `gitlab-runner register` не нужна: с GitLab 16 раннер заводится в
интерфейсе, а `register` — прежний способ, где токен выдавался на группу.

### Если на машине уже есть другой раннер

Имена контейнеров compose составляет из имени проекта — по умолчанию это имя
папки. Столкнуться они могут только если папка названа так же. Задать имя явно:

```bash
echo "COMPOSE_PROJECT_NAME=study-platform-runner" > .env
docker compose up -d
```

Два раннера на одной машине уживаются спокойно: у каждого свой конфиг, свой
токен и свой набор тегов, а контейнеры джоб они просто создают через общий
демон.

Что действительно стоит решить — уборку. Она чистит демон целиком, а не только
наши образы, так что недельный кеш соседнего проекта тоже уйдёт. Если это
нежелательно, поднимать только раннер:

```bash
docker compose up -d runner
```

Тогда следить за диском придётся самому — `docker system df`.

## Сколько джоб одновременно

`concurrent` в `config.toml`. Считать по памяти: сборка фронтенда — около двух
гигабайт, остальное заметно легче. На четырёх гигабайтах ставить 2, на восьми —
4. Больше четырёх смысла нет: матрица сборки всё равно из четырёх джоб.

Если сборка начнёт вытеснять с машины всё остальное, в `[runners.docker]` есть
закомментированные `memory` и `cpus`.

## Почему сокет, а не docker-in-docker

Джобам отдан `/var/run/docker.sock` хоста. Размен осознанный: джоба получает
полный доступ к docker этой машины, то есть фактически root на ней. Взамен два
выигрыша — слои остаются между сборками (вторая сборка того же образа занимает
секунды вместо минут) и не нужен привилегированный контейнер, который в смысле
изоляции ничем не лучше.

Для сборочной машины, где выполняется только свой код, это нормально. Если на
ней когда-нибудь будут собираться чужие мерж-реквесты — вернуть dind:
в `config.toml` поставить `privileged = true` и убрать сокет из `volumes`,
а в `.gitlab-ci.yml` вернуть джобе `build`:

```yaml
  image: docker:27
  services:
    - docker:27-dind
  variables:
    DOCKER_DRIVER: overlay2
```

## Уборка

Второй контейнер, `prune`, раз в сутки убирает образы и кеш сборок старше
недели. Без него диск кончается незаметно. Неделя выбрана не наугад: свежий
`latest` нужен джобе `build` как источник слоёв для `--cache-from`, когда
локального кеша не оказалось.

Уборка идёт по всему демону: отличить наши образы от чужих ей нечем. На машине
с одним раннером это то, что нужно; при соседях — см. выше.

Посмотреть, сколько занято:

```bash
docker system df
```

## Обновление раннера

Версия закреплена намеренно: `latest` однажды уедет вперёд и джобы начнут
падать без внятной причины. Раннер и gitlab.com должны совпадать по мажорной
версии.

```bash
# поменять тег в docker-compose.yml, затем
docker compose pull && docker compose up -d
```

## Что этот раннер умеет делать с продом

Ничего сам по себе. Выкладка идёт из джобы `deploy`, которая берёт ssh-ключ из
переменных проекта в GitLab и ходит на прод-сервер. Раннер лишь выполняет эту
джобу, так что доступ к проду определяется тем, кто может запустить пайплайн на
`main`, а не тем, у кого есть доступ к этой машине.

Но помнить стоит: ключ от прода на время джобы оказывается в контейнере на этой
машине. Держать её так же аккуратно, как прод.
